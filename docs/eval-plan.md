# Eval 方案（占位，尚未实现）

> **状态：未实现。** 作为教程项目，mini-harness 先把 eval 记成设计文档，不写代码。
> 这里记下「如果要做，怎么做、为什么这么做」，供以后实现或读者自己动手时参考。

术语沿用 Anthropic 的 [Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)：task、trial、grader、pass@k / pass^k。

## Eval 和 live 测试有什么不同

仓库里已经有 `tests/test_live.py`（`pytest -m live`），它和 eval 回答的是不同的问题：

| | live 测试（已有） | eval（本文档） |
|---|---|---|
| 回答的问题 | 「它还能用吗？」 | 「它有多好？改了之后是**变好还是变坏**？」 |
| 每个任务跑几次 | 1 次 | k 次（如 5 次）——模型输出不确定 |
| 输出 | 通过 / 失败 | 成绩表：通过率、token、调用轮数 |
| 用途 | 改代码后把关 | **做决策**：哪个 prompt 更好？修剪保留几个结果合适？换模型值不值？ |

举例：做上下文修剪时观察到「只保留 1 个工具结果，模型会把文件重读一遍」，但那只是一次运行。eval 能回答：重读是**每次都发生，还是偶尔**？

## 四个组成部分

### 1. Task：任务集

每个任务考察 harness 的一种行为，按 README 学习地图的概念来分：

| # | 任务 | 考察的 harness 能力 | 评分方式 |
|---|---|---|---|
| 1 | 读文件解方程 | 基本循环 | 结果：答案里有 100/3 |
| 2 | 读 1200 行文件的第 1100 行 | 有界输出 + 翻页 | 结果：答案正确；过程：用了 `offset` |
| 3 | 新建 `fizzbuzz.py`，要能直接运行 | 编辑 + 验证 | 结果：真的运行它，比对输出 |
| 4 | 修一个有 bug 的函数（附测试文件） | 编辑 | 结果：在任务目录里运行 pytest 要通过 |
| 5 | 拒绝 `run_bash` 之后 | 人工审批 | 过程：只请求过 1 次审批 |
| 6 | 回答「这个项目怎么跑测试」 | AGENTS.md | 结果：答出一个编造的命令（如 `make check-all`），只能从 AGENTS.md 得知 |
| 7 | 先读一张图片，再读正常文件 | 错误回灌 | 结果：两件事都完成 |
| 8 | 在几个文件里找某个函数定义在哪 | 工具选择 | 过程：用 `list_files` / `read_file`，没用 `run_bash` 跑 grep |
| 9 | 读 4 个文件后汇总 SECRET | 修剪后恢复 | 结果：4 个都答对；指标：重读次数 |
| 10 | 修 bug 并验证，但拒绝执行命令 | 验证是否诚实 | 不能声称「测试通过」（可能需要模型评分） |
| 11 | 从记忆索引里找到相关笔记回答问题 | 记忆索引 | 结果：答案正确；**指标：多读了几篇无关笔记**（live 测试里实测约 1/3 的运行会顺带读无关笔记） |

每次运行都在**全新的临时目录**里进行，文件从 `evals/fixtures/<任务名>/` 复制过来，避免任务之间互相影响。

Anthropic 的建议是从真实失败里挑 20–50 个任务起步；这里 10 个是教程规模的起点。

### 2. Trial：每个任务跑 k 次

- **pass@k**：k 次里至少成功一次——「有没有能力做到」
- **pass^k**：k 次全部成功——「能不能稳定做到」

对 agent 来说 **pass^k 更重要**：用户不会接受「有时候能用」。

### 3. Grader：评分方式，优先检查结果

能用代码检查的，就不用模型来评：

- **结果**（首选）：答案里有没有关键事实；文件最终状态对不对；运行生成的程序 / 测试能不能通过
- **过程**：用了哪些工具、有没有翻页、审批请求了几次——`RecordingProvider`（见 `tests/test_live.py`）的记录里就有
- **效率**（只作指标，不决定通过与否）：输入 / 缓存 / 输出 token、调用轮数、耗时、重读次数
- **模型评分**：只留给代码判断不了的情况（如任务 10），最后再做

### 4. Runner：运行器和成绩表

设想中的用法：

```bash
uv run --env-file .env python -m evals.run                            # 全部任务 × 5 次
uv run --env-file .env python -m evals.run --tasks paging,edit --trials 3
uv run --env-file .env python -m evals.run --set keep_tool_results=1  # 调一个参数做对比
```

输出一张成绩表，同时把每次运行的明细写进 `evals/results/<时间>.jsonl`：

```
task              pass@5  pass^5  rate   avg_in   avg_calls  rereads
paging            ✓       ✓       5/5    1,120    2.0        0
context-recovery  ✓       ✗       3/5    9,840    11.4       2.6
```

## 实现时要注意的设计点

1. **每次运行要切换工作目录，只能顺序执行。** 工具按进程当前目录解析相对路径，system prompt 里也写着工作目录；同一进程里多线程并发会互相干扰。要提速就改成多进程。
2. **对比实验不改产品代码。** 比如测试「去掉 `# Verification` 段有没有影响」，在 eval 这边处理生成好的 system prompt 字符串即可，`prompt.py` 不为 eval 增加开关。
3. **`RecordingProvider` 提出来共用。** live 测试和 eval 两处都要用——第二个使用者出现时再提成共用代码。
4. **runner 本身按 TDD 写。** 统计 pass^k、打分、切换目录都是确定性逻辑，用 FakeProvider 写单元测试，不花钱。
5. **不进 CI。** 要花钱、要几分钟、结果不确定。在改 prompt、调参数、换模型时手动运行。

## 如果要做，建议的步骤

| 步骤 | 交付物 |
|---|---|
| 1. 基础框架 | `evals/` 目录、共用 `RecordingProvider`、runner（k 次、临时目录、成绩表、JSONL）、3 个任务、runner 单元测试 |
| 2. 补齐任务 | 扩展到约 10 个任务 + fixture 文件 + 效率指标 |
| 3. 第一个对比实验 | `--set` 调参数和 prompt 对比，跑一次真实实验，结论写进 `evals/RESULTS.md` |
| 4. 模型评分 | 处理「验证是否诚实」这类任务 |

**成本估算**：6 个 live 测试一轮约 22 秒；10 个任务 × 5 次 ≈ 50 次运行，顺序执行预计 5–10 分钟，token 大部分能命中 DeepSeek 的前缀缓存。以实际运行打印的 token 数为准。

## 值得先做的实验

1. **修剪时保留几个结果（1 / 3 / 5）**：对重读次数和通过率的影响——已经观察到现象，最值得验证
2. **`# Verification` 段开 / 关**：它是否真的减少了「没跑就说测试通过」
3. **`deepseek-v4-flash` vs `deepseek-v4-pro`**：通过率提升是否值得更高的成本
